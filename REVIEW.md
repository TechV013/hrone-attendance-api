# REVIEW.md

The locations below refer to the supplied starter `app/main.py`.

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `health` | It returned `200` without checking MongoDB, despite the readiness contract. | Stop MongoDB and call `GET /health`; it still reported ready. | Ping MongoDB and return `503` if it is unavailable or indexes are not ready. |
| 2 | Startup / indexes (missing) | No indexes were created, so the natural keys were not enforced and queries could scan entire collections. | Inspect indexes; issue duplicate or concurrent creates; run explain on a large dataset. | Create idempotent indexes at startup, including unique `employees.emp_code` and unique `(attendance_logs.emp_code, attendance_logs.date)`. |
| 3 | `create_employee` | Check-then-insert was not safe for concurrent duplicate requests. | Send two creates for the same `emp_code` simultaneously. | Rely on the unique index and translate `DuplicateKeyError` into `409`. |
| 4 | `EmployeeIn` | Input validation did not enforce the employee code, email, date, shift-time formats, field limits, or distinct shift times. | Submit `EMP1`, an invalid date, malformed email, or identical shift endpoints. | Add Pydantic constraints and calendar-date / shift-duration validation. |
| 5 | `create_employee` | `created_at` was a naive local datetime and was returned as a datetime rather than epoch milliseconds. | Create an employee in a non-UTC environment and inspect its response. | Store a UTC instant and serialize all API instants as integer epoch milliseconds. |
| 6 | `list_employees` | `skip = page * page_size` skipped the first page, the result was unsorted, and `total` ignored the department filter. | Request page 1 and compare totals for a department filter. | Use `(page - 1) * page_size`, sort by `emp_code`, and count the filtered query. |
| 7 | `compute_late_minutes` | The helper used the host-local punch timestamp as though it were the shift's IST clock time. Its whole-minute grace check also mishandled seconds just beyond the 10-minute boundary. | For a 09:30 shift, try 09:40:01 IST or run the API on a non-IST host. | Normalize instants to UTC, calculate against the IST shift start, truncate to seconds, and apply the strict 600-second grace rule. |
| 8 | `compute_work_hours` | Binary-float `round` can use ties-to-even rather than the required half-up rounding. | Test a duration whose hours are exactly halfway between two hundredths. | Use `Decimal` with `ROUND_HALF_UP`. |
| 9 | `compute_overtime` | It put an overnight shift end on the attendance date and mixed naive and timezone-aware datetimes; it also missed the 30-minute minimum. | Test a 22:00–06:00 shift with punch-out at 06:29 and 06:30 IST. | Build the shift-end instant on the correct IST date and count whole minutes only when the result is at least 30. |
| 10 | `punch_in` | An unknown employee was dereferenced without a check, producing a server error instead of `404`. | Punch in with an unknown `emp_code`. | Return `404` before using the employee's shift fields. |
| 11 | `PunchInIn` / `punch_in` | Timestamp values were coercive, local-time based, and selected by truthiness; a valid instant of `0` could silently become “now”, while seconds-looking values were not properly rejected. | Try a float, string, seconds timestamp, explicit null, or a timestamp with milliseconds. | Use strict bounded integer milliseconds, reject explicit null, convert in UTC, and truncate to whole seconds. |
| 12 | `punch_in` | A read-before-insert duplicate check allowed two concurrent requests to create the same employee/date record. The attendance date also ignored the overnight R1 rule. | Race two punch-ins, or punch in at 03:00 IST on a 22:00–06:00 shift. | Let the unique natural-key index arbitrate races and derive the attendance date in IST, assigning overnight early-morning punches to the previous shift date. |
| 13 | `punch_in` / `list_attendance` | Responses exposed an `id` derived from MongoDB `_id` even though the contract uses `(emp_code, date)` and specifies no attendance ID. BSON datetimes were also returned instead of epoch milliseconds. | Compare response keys and timestamp types with `openapi.yaml`. | Serialize explicit public fields, omit `_id` and `id`, and convert all instants, including nested history timestamps, to epoch milliseconds. |
| 14 | `list_attendance` | It loaded all matching documents into Python, sorted there, and only then paginated; it also omitted the secondary `emp_code` sort. | Use a large date range and inspect memory/query work; create equal-date records. | Apply filters, indexed sort, skip, and limit in MongoDB; calculate `total` from the filtered query. |
| 15 | Missing endpoint implementations | Punch-out, regularization, all four analytics routes, and explain were TODOs. | Call any of those contract paths. | Implement the missing routes, including aggregation-backed analytics and raw execution-stats explain output. |
| 16 | `regularizeAttendance` (missing) | There was no recomputation or append-only audit trail, and no protection against competing edits losing history. | Correct a punch time, inspect `history`, then issue concurrent corrections. | Recompute derived fields, append exactly one before/after audit entry, and use optimistic compare-and-set matching that includes the history snapshot. |
| 17 | Pagination and query parameters | The starter had no `page_size` upper bound and did not validate date ranges or enforce the response contract's status/timestamp types. | Use page size 101, reversed date bounds, or an invalid status. | Add FastAPI/Pydantic range and enum validation, and return `422` for reversed bounds. |

## Reviewed and retained

- `load_dotenv(override=False)` is appropriate: variables supplied by the process environment take precedence over local `.env` values.
- Keeping the human business key `emp_code` separate from MongoDB `_id` is the correct data-model choice; the fix is to enforce that convention consistently in indexes and responses.
- The supplied status vocabulary is retained exactly: `PRESENT`, `WFH`, and `ON_DUTY` are presence statuses; `ABSENT` and `LEAVE` are not.
